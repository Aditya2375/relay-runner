03 / CHOOSE THE RIGHT TOOL

One project.
Two different boundaries.

The signed-task transport and coding loop do not have the same powers. Choose deliberately.

A
SIGNED TASKS / NO MODEL REQUIRED

A small, fixed vocabulary.

Sign a job locally or send it over loopback HTTP. The runner checks its signature, age and one-time ID, then dispatches one of four registered tasks.

system.summaryworkspace.listnotes.appendcommand.node-version

Command access is off by default. For this transport, enabling it permits only the fixed node --version template. Not a general shell.

B
CODING LOOP / BRING A MODEL

Plan. Review. Run. Repeat.

A model proposes the next step. Review file changes and command requests before they run, or explicitly approve that action type for the rest of a run. A step cap keeps the loop bounded.

read_filewrite_filerun_command

Approved shell commands are not sandboxed. They can access your machine with your user privileges. Command execution also needs --enable-commands.

04 / READ BEFORE RUNNING

Control is a practice.
Not a promise.

Local does not mean isolated. A signature does not make an agent trustworthy. This is a teaching prototype, not a production security boundary.

Read the full boundaries ↗
01

Inspect your workspace.

Hosted model modes send project content to your chosen provider. Common secret files are excluded, but the filter is not a secret detector.

02

Keep command access narrow.

Agent-mode shell commands are not confined by the file-path guard. Read the exact command before approving it. Keep command mode off when you do not need it.

03

Protect the local key.

A process running as your OS user may read the signing key and impersonate a sender. Loopback HTTP is not protection from other local processes.

04

Review the record.

Run logs include tasks, decisions and model exchanges. Treat them as potentially sensitive files, not harmless diagnostics.
